<SectionHeading title="Background" />

Feature releases and experiments were spread across client code, deployments, internal documents, Slack conversations, and individual memory. What first looked like separate operational inconveniences was one fragmented workflow.

By observing how the team actually worked, I connected release control, experiment context, and lifecycle monitoring as parts of the same system. I initiated the project and led it from problem discovery through implementation.

# 01. Identifying Problems

I traced recurring moments of friction back through the workflow, then tested whether they were isolated requests or symptoms of the same system.

<SectionHeading eyebrow="Identifying Problems" title="Incidents" />

### A. Slow shutdown

- _No targeted shutdown_ — Disabling one feature still required a code change, build, deployment, and verification.
- _Unsafe rollback_ — Reverting the deployment also removed unrelated, healthy features shipped alongside it.

<Figure
  src="./images/slow-shutdown.png"
  alt="Billie, Kit, and Bucky ship in one deployment. When Billie fails, rolling back also disables the two healthy features, while keeping the deployment requires a slower code change and redeployment."
  caption="The team could not disable Billie independently: rollback affected every feature in the deployment, while a targeted fix kept users exposed to the error."
  width={1672}

/>

### B. Manual experiments

- _Engineer-dependent QA_ — Testing another variant required database access, account changes, or help from an engineer.
- _Deployment-bound operations_ — Rollout and variant changes repeatedly created avoidable deployments.
- _Frequent context switching_ — Small requests interrupted engineering work and reduced focus.

<Figure
  src="./images/manual-experiments.png"
  alt="A reconstructed Slack conversation where QA repeatedly asks an engineer to switch experiment variants and a product manager requests a rollout increase that requires another deployment."
  caption="Reconstructed from recurring team requests. Routine QA and rollout changes depended on engineers modifying assignments, code, and deployments."
  width={1672}
  height={941}
/>

### C. Missed checkpoints

- _Delayed validation_ — Instrumentation checks happened only when an engineer remembered them.
- _Reactive analysis_ — Results were prepared after someone requested them, sometimes too late for a meeting.
- _Lost context_ — Each analysis required the team to reconstruct decisions scattered across memory and documents.

  src="./images/missed-checkpoints.png"

<SectionHeading eyebrow="Identifying Problems" title="Synthesis" />

The data converged on four connected system conditions.

1. _Code-bound control_  
   Deployment and release were treated as the same operation.
2. _Engineering dependency_  
   Routine experiment operations required developer intervention.
3. _Unstable assignment_  
   Configuration changes could alter an existing user's experience.
4. _Memory-based operation_  
   Monitoring progressed only when someone remembered the next step.

> The team could ship experiments, but could not reliably control, preserve, and
> monitor them across their lifecycle.
