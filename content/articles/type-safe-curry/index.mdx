# 0. Functional Programming and Currying

While studying functional programming, I came across _currying_. At first, it
looked like little more than a technique for breaking a complex function into
smaller ones. The further I followed it, however, the more it seemed to capture
_several ideas at the heart of functional programming_.

<SectionHeading title="The Principles Behind Functional Programming" />

Functional programming tends to emphasize:

- functions as first-class values,
- immutability,
- pure functions,
- declarative programming,
- composition and modularity, and
- higher levels of abstraction.

Together, these principles model a program as _a flow of data and
transformations_.

<SectionHeading title="What Is Currying?" />

Currying transforms _a function of N arguments into a sequence of N functions,
each accepting one argument_. The name comes from the mathematician Haskell
Curry.

```typescript
// A regular two-argument function
const add = (a: number, b: number) => a + b;
add(1, 2); // 3

// Its curried form
const curriedAdd = (a: number) => (b: number) => a + b;
curriedAdd(1)(2); // 3
```

`add` receives both arguments at once. `curriedAdd` receives `a`, returns
another function, and lets that function receive `b`.

<SectionHeading title="Why Currying Fits Functional Programming" />

_Functions become values_

A curried function returns another function, making _first-class functions
visible in everyday code_:

```typescript
const multiply = (a: number) => (b: number) => a * b;
const double = multiply(2);

double(5); // 10
```

`double` is a reusable value produced from a more general function.

_Immutability and pure functions remain natural_

Partial application _creates a new function without modifying the original one_.
Each step returns a value rather than mutating external state.

_Composition and reuse become easier_

Currying produces _unary functions that fit naturally into composition_:

```typescript
const curry = (fn: Function) => (a: unknown) => (b: unknown) => fn(a, b);
const add = (a: number, b: number) => a + b;
const curriedAdd = curry(add);

const add3 = curriedAdd(3);

[1, 2, 3, 4, 5].map(add3); // [4, 5, 6, 7, 8]
```

`add3` fixes one argument of `add`, producing a smaller function with a clearer
purpose.

_General operations can become specific tools_

```typescript
const filterBy =
  (predicate: (value: number) => boolean) => (values: number[]) =>
    values.filter(predicate);

const isEven = (value: number) => value % 2 === 0;
const filterEven = filterBy(isEven);

filterEven([1, 2, 3, 4, 5, 6]); // [2, 4, 6]
```

`filterBy` is a reusable higher-order function. Partial application turns it
into `filterEven`, a function that expresses one concrete operation.

_Intent becomes more declarative_

```typescript
const greaterThan = (min: number) => (value: number) => value > min;
const filterGreaterThan10 = filterBy(greaterThan(10));

filterGreaterThan10([5, 12, 8, 20, 3]); // [12, 20]
```

`greaterThan(10)` describes _what_ qualifies. `filterBy` handles _how_ the array
is traversed.

Many functional utility libraries provide `curry` as a foundation. Looking at
the implementation in Rambda left me with a question: what would it take to
build _the same flexibility with useful TypeScript inference_?

# 1. Defining the Curry Function

<SectionHeading title="1.1. Strict Curry or Loose Curry?" />

There are two common calling styles:

- _Strict curry_ accepts exactly one argument at each step.
- _Loose curry_ accepts one or more arguments at each step.

Haskell is designed around functional programming, and all of its functions are
curried by default. Even a function that appears to accept several arguments
behaves as _a chain of unary functions_:

```haskell
add :: Int -> Int -> Int
add x y = x + y

add3 = add 3
result = add3 5 -- 8
```

`add 3` returns a function that remembers `x = 3`; `add3 5` supplies the second
argument. The syntax permits `add 3 5`, but the model remains a sequence of
single-argument applications.

That consistency makes behavior predictable and composition natural. In
JavaScript, though, forcing every caller to use nested single-argument calls can
be inconvenient. Loose currying preserves partial application while allowing a
_more practical calling style_, so that is what I chose to build:

```typescript
const sum = (a: number, b: number, c: number) => a + b + c;
const curriedSum = curry(sum);

curriedSum(1)(2)(3);
curriedSum(1, 2)(3);
curriedSum(1, 2, 3);
```

<SectionHeading title="1.2. The Runtime Implementation" />

The runtime design is simple: _collect arguments until there are enough to call
the original function_. Otherwise, return another curried function and continue
recursively.

```typescript
type AnyFunc = (...args: any[]) => any;

const isComplete = (args: any[], expectedLength: number): boolean =>
  args.length >= expectedLength;

function curry(fn: AnyFunc, ...collectedArgs: Partial<Parameters<AnyFunc>>) {
  return (...newArgs: any[]) => {
    const allArgs = [...collectedArgs, ...newArgs];

    return isComplete(allArgs, fn.length)
      ? fn(...allArgs)
      : curry(fn, ...allArgs);
  };
}
```

The variables have distinct roles:

- `collectedArgs` contains arguments from earlier calls.
- `newArgs` contains arguments supplied by the current call.
- `allArgs` combines both groups.

```text
curry(sum)
  └─ call(1)
      └─ call(2)
          └─ call(3)
              └─ sum(1, 2, 3) = 6
```

`isComplete` compares the number of collected arguments with `fn.length`. When
there are enough, the original function runs. Otherwise, `curry` returns
another function and keeps collecting.

<SectionHeading title="1.3. The First Building Blocks" />

`AnyFunc` is a convenient unconstrained function type:

```typescript
type AnyFunc = (...args: any[]) => any;
```

`Parameters<Fn>` extracts a function's arguments as a tuple:

```typescript
type Example = (a: number, b: string, c: boolean) => void;
type Params = Parameters<Example>;
// [number, string, boolean]
```

At first, `Partial<Parameters<Fn>>` looks like a good model for
`collectedArgs`, because a curried call may have supplied only some parameters:

```typescript
type PartialParams = Partial<[number, string, boolean]>;
// [number?, string?, boolean?]
```

That gets the runtime structure working, but _the function is still not type
safe_.

# 2. Making the Input Generic

<SectionHeading title="2.1. The Problem with any" />

The first implementation accepts every value:

```typescript
const sum = (a: number, b: number, c: number) => a + b + c;
const curriedSum = curry(sum);

const addThree = curriedSum(1)(2);
addThree("a"); // Runtime result: "3a"
```

TypeScript should reject the string, but every argument has already widened to
`any`.

<SectionHeading title="2.2. Capturing the Original Function Type" />

Making the input function generic allows the implementation to _retain its
parameter tuple_:

```typescript
function curry<Fn extends AnyFunc>(
  fn: Fn,
  ...collectedArgs: Partial<Parameters<Fn>>
) {
  return (...newArgs: any[]) => {
    const allArgs = [...collectedArgs, ...newArgs];

    return isComplete(allArgs, fn.length)
      ? fn(...allArgs)
      : curry(fn, ...allArgs);
  };
}
```

Now `collectedArgs` is constrained by the parameters of the specific `Fn`
passed to `curry`.

# 3. Partial Tuples and Rest Parameters

<SectionHeading title="3.1. “A Rest Parameter Must Be of an Array Type”" />

Typing `collectedArgs` as `Partial<Parameters<Fn>>` exposes another problem:

<Figure
  src="./images/partial-rest-error.png"
  alt="TypeScript error stating that a rest parameter must be of an array type."
  caption="The mapped Partial type is not accepted directly as the type of a rest parameter."
  width={806}
  height={246}
/>

Conceptually, `Partial` makes each tuple position optional:

```typescript
type Example = (a: number, b: string, c: boolean) => void;
type Params = Parameters<Example>;
// [number, string, boolean]

type PartialParams = Partial<Params>;
// [number?, string?, boolean?]
```

For a rest parameter, however, TypeScript needs a type it can confidently treat
as an array or tuple. I wanted an explicit tuple transformation that preserved
_both ordering and optional positions_.

<SectionHeading title="3.2. Building PartialTuple" />

The target behavior is:

```typescript
type Example = [number, string, boolean];
type Result = PartialTuple<Example>;
// [number?, string?, boolean?]
```

Ordering matters here for more than satisfying the rest parameter. Currying
_applies parameters from left to right_. A caller may stop after any prefix, but
should not skip earlier positions and supply a later one in isolation:

```typescript
type Example = (a: number, b: string, c: boolean) => void;

curry(example)(1);
curry(example)(1, "hello");
curry(example)(1, "hello", true);

curry(example)(true); // Type error
```

`PartialTuple` recursively moves values from `Params` into an accumulator,
marking each position as optional:

```typescript
type PartialTuple<
  Params extends any[],
  Accumulated extends any[] = []
> = Params extends [infer CurrentParam, ...infer RemainingParams]
  ? PartialTuple<RemainingParams, [...Accumulated, CurrentParam?]>
  : [...Accumulated, ...Params];
```

Applied to the implementation:

```typescript
function curry<Fn extends AnyFunc>(
  fn: Fn,
  ...collectedArgs: PartialTuple<Parameters<Fn>>
) {
  return (...newArgs: any[]) => {
    const allArgs = [...collectedArgs, ...newArgs];

    return isComplete(allArgs, fn.length)
      ? fn(...(allArgs as Parameters<Fn>))
      : curry(fn, ...(allArgs as PartialTuple<Parameters<Fn>>));
  };
}
```

The rest-parameter error disappears, and _invalid parameter order can be
rejected at the type level_.

<SectionHeading title="3.3. How PartialTuple Recurses" />

The four generic names describe the recursion:

- `Params`: parameters still waiting to be processed.
- `Accumulated`: parameters already converted.
- `CurrentParam`: the first parameter in the current step.
- `RemainingParams`: every parameter after it.

```text
PartialTuple<[number, string, boolean]>
→ PartialTuple<[string, boolean], [number?]>
→ PartialTuple<[boolean], [number?, string?]>
→ PartialTuple<[], [number?, string?, boolean?]>
→ [number?, string?, boolean?]
```


    The second step extracts `string` and appends `string?`.

    ```typescript
    PartialTuple<[boolean], [number?, string?]>
    ```

    ```typescript
    PartialTuple<[], [number?, string?, boolean?]>
    ```

# 4. Requiring at Least One Argument

<SectionHeading title="4.1. Why Empty Calls Should Be Invalid" />

Currying is useful because it partially applies an original function. _A call
that supplies no arguments makes no progress_:

```typescript
const add = (a: number, b: number, c: number) => a + b + c;
const curriedAdd = curry(add);

curriedAdd(); // This should be a type error.
```

This can be prevented before runtime.

<SectionHeading title="4.2. AtLeastOneParam" />

`AtLeastOneParam` keeps the first parameter required and makes every remaining
position optional:

```typescript
type AtLeastOneParam<Fn extends AnyFunc> = Parameters<Fn> extends [
  infer Head,
  ...infer Tail
]
  ? [Head, ...Partial<Tail>]
  : never;
```

If `Fn` takes no arguments, the type resolves to `never` and prevents a curried
call. Otherwise:

```typescript
type Fn = (a: number, b: string, c: boolean) => void;
type Result = AtLeastOneParam<Fn>;
// [number, string?, boolean?]
```

This shape supports loose partial application while _guaranteeing that every
call contributes at least one value_.

# 5. Deriving the Curried Return Type

The runtime function is ready, but its return type still needs to describe two
different outcomes:

1. _If parameters remain_, return another curried function.
2. _If every parameter has been supplied_, return the original result.

<SectionHeading title="RemainingParameters" />

First, `RemainingParameters` removes one expected parameter for each applied
argument:

```typescript
type RemainingParameters<
  AppliedArgs extends any[],
  ExpectedArgs extends any[]
> = AppliedArgs extends [any, ...infer RestApplied]
  ? ExpectedArgs extends [any, ...infer RestExpected]
    ? RemainingParameters<RestApplied, RestExpected>
    : []
  : ExpectedArgs;
```

For example:

```typescript
type Result = RemainingParameters<[number, string], [number, string, boolean]>;
// [boolean]
```

The recursion _consumes both tuples in parallel_. When there are no applied
arguments left, the remaining expected tuple is the answer.

<SectionHeading title="CurriedFunction" />

`CurriedFunction` uses that remaining tuple to decide what the next call
returns:

```typescript
type CurriedFunction<Fn extends AnyFunc> = <
  AppliedParams extends AtLeastOneParam<Fn>
>(
  ...args: AppliedParams
) => RemainingParameters<AppliedParams, Parameters<Fn>> extends [any, ...any[]]
  ? CurriedFunction<
      (
        ...args: RemainingParameters<AppliedParams, Parameters<Fn>>
      ) => ReturnType<Fn>
    >
  : ReturnType<Fn>;
```

`AppliedParams` must contain at least one valid parameter. If
`RemainingParameters` contains at least one element, the return value is another
`CurriedFunction` whose input is the remaining tuple. When nothing remains, the
return value becomes `ReturnType<Fn>`.

The implementation can now declare the complete return type:

```typescript
function curry<Fn extends AnyFunc>(
  fn: Fn,
  ...collectedArgs: PartialTuple<Parameters<Fn>>
): CurriedFunction<Fn> {
  return ((...newArgs: any[]) => {
    const allArgs = [...collectedArgs, ...newArgs];

    return isComplete(allArgs, fn.length)
      ? fn(...(allArgs as Parameters<Fn>))
      : curry(fn, ...(allArgs as PartialTuple<Parameters<Fn>>));
  }) as CurriedFunction<Fn>;
}
```

# 6. The Finished API

The final type supports flexible grouping _without losing parameter order,
argument types, or the original return type_:

```typescript
const sum = (a: number, b: number, c: number) => a + b + c;
const curriedSum = curry(sum);

const one = curriedSum(1);
const three = one(2);
const six = three(3); // number

curriedSum(1, 2)(3); // number
curriedSum(1)(2, 3); // number
curriedSum(1, 2, 3); // number

curriedSum(); // Type error
curriedSum("1"); // Type error
curriedSum(1)("2"); // Type error
```

The runtime behavior was the easy part: collect arguments and recurse until
`fn.length` is satisfied. _The real work was expressing the same state machine
in the type system._

_Recursive tuple types turned out to be a natural fit._ `PartialTuple` models the
prefix collected so far, `AtLeastOneParam` guarantees progress on every call,
and `RemainingParameters` determines whether the next value should be another
function or the final result.

The complete implementation is also available in the
[`function-al` project](https://hwanheejung.tistory.com/78).
