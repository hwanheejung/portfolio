## TL;DR

- _Objects are self-responsible entities._ OOP design structures them like an ecosystem, where small objects collaborate to create larger capabilities.
- _Good object design reveals responsibility through names._ Object names should be nouns that express responsibility and identity, avoiding instrumental labels such as `-er`. Methods should distinguish between _noun-like builders_ that return new objects and _verb-like manipulators_ that change state. Treat _side-effect-free values like properties_, but make _state changes or external effects explicit as methods_.
- _An object's identifier is an immutable coordinate_ that distinguishes it in the world and preserves its identity, so it should be encapsulated from external change. When objects have the same state, they can be treated as having the same meaning even if they are different instances in memory, improving predictability, testability, cache efficiency, and concurrency safety.
- _Design objects to be immutable whenever possible_: return new objects rather than changing state, for greater predictability, concurrency safety, and simplicity. A faithful object does not change itself, but models the world honestly by reflecting changes in the external entity through the same identifier. Unlike constant objects, whose state is their identifier, mutable objects need a separate identifier to preserve their identity.
- _Good collaboration begins with depending on contracts_ rather than implementations. Interfaces are the rules of an object society, reducing coupling and allowing the system to evolve.

# 1. Respecting Objects Starts with Naming Them Carefully

<SectionHeading title="1.1. Naming Is the First Sign of Respect" />

Object-oriented design is ultimately a language of _respect_. An object is not
just a data structure. It is a responsible participant: we entrust it with
work, expect something from it, and ask it to collaborate with other objects.

The first thing we can do as designers is give an object a name worthy of that
role. Its name should reveal its responsibility and identity. We should be able
to look at the name and understand who the object is and what role it plays.

An object's name comes before the object itself. It is more than an explanation
for the client that uses it; it also reveals the designer's attitude and how
the designer understands the object.

<SectionHeading title="1.2. Avoid -er in Class Names" />

Adding `-er` to a class name can reduce an object to a utility that works for
someone else:

```javascript
class Parser {} // Feels like a tool that works for someone
class ParsedCell {} // Represents a meaningful result and its state
```

The same idea leads to names such as:

- `UserRegisterer` → `Registration`
- `Manager` → `Project`
- `Sender` → `Message`

The `-er` suffix can turn an object into a wrapper around a helper function
without revealing its identity or responsibility. An object should not merely
assist another object. It should own a responsibility and act on its own.

<SectionHeading title="1.3. Name Methods Carefully Too" />

Class names are not the only names that matter. Our understanding of an object
also appears in its method names.

Methods can be divided into two broad categories:

<Columns gap="wide">
  <Column>
    **Builder**

    - creates or transforms something and returns a new object,
    - always has a return value,
    - does not change internal state, and
    - uses a name that describes the resulting object.

  </Column>
  <Column>
    ```typescript
    class Book {
      withAuthor(author: string): Book {}
      withTitle(title: string): Book {}
    }

    const book1 = new Book();
    const book2 = book1.withTitle("The Elegant Object");
    const book3 = book2.withAuthor("Yegor Bugayenko");
    ```

    `book1` does not change. Each builder returns a new object, preserving
    immutability while allowing objects to be composed.

  </Column>
</Columns>

<Columns gap="wide">
  <Column>
    **Manipulator**

    - changes an entity or some state in the real world,
    - returns no value,
    - uses a verb, such as `save`, `put`, `remove`, or `quicklyPrint`, and
    - makes the state-changing action clear.

  </Column>
  <Column>
    ```typescript
    printer.save();
    printer.quicklyPrint();
    printer.remove("trash.txt");
    ```

    The action itself is the manipulator's responsibility.

  </Column>
</Columns>

<SectionHeading title="1.4. Separate Commands and Queries" />

CQS stands for _Command–Query Separation_.

> A method that changes state—a command—should not return a value. A method that
> returns a value—a query—should not change state.

In other words, one method should have one responsibility.

- `saveAndReturnId()` saves state and returns a value at the same time.
- `updateAndLog()` combines a change with another side effect.

<SectionHeading title="1.5. Can a Method Look Like a Property?" />

Some methods feel as though they could be properties:

```typescript
const count = items.length;
const price = cart.totalPrice();
```

From the outside, it does not matter whether a value was calculated or stored.
If it represents an attribute, it can look like a property.

- A simple attribute can be exposed as a property.
- A computed value can use a getter if reading it has no side effects.
- If reading the value changes something internally or affects the outside
  world, method syntax should make that behavior explicit.

<SectionHeading title="1.6. Summary" />

- A class name should reveal an object's identity and responsibility.
- Avoid `-er` where it reduces an object to a tool; prefer a noun that
  represents its role.
- Distinguish builders from manipulators.
- Give each method one responsibility through CQS.
- Treat information that behaves like an attribute as an attribute, but make
  side effects explicit with method syntax.

  Must an immutable object's builder always have a noun-like name? How can we
  choose builder names that clearly describe the new object they return?
</Callout>

# 2. An Object's Identifier Is Its Coordinate in the World

An object is not just a collection of state. It needs a meaningful position,
and that position is its _identifier_.

<SectionHeading title="What Exactly Is an Identifier?" />

An identifier distinguishes an object from the rest of the world. Its stability
allows the object to remain the same object over time. It acts like a
coordinate, an identity, or an address.

Consider a person. Their home address can change, but their government-issued
identifier does not. Whether they live in Seoul or Gwangju, they remain the
same person. The address is state; the identifier preserves identity.

<SectionHeading title="Changing the Identifier Creates a Different Object" />

An identifier gives an object continuity. If the identifier changes, the object
becomes another object.

```typescript
user.id = "new-id"; // A mutable ID destroys the object's identity
```

The identifier should therefore be immutable. At least the state that defines
the object's identity should not be changeable from outside. This is where
encapsulation matters.

Private fields provide one way to encapsulate state:

```typescript
class Cash {
  #digits;
  #cents;
  #currency;

  constructor(digits, cents, currency) {
    this.#digits = digits;
    this.#cents = cents;
    this.#currency = currency;
  }
}
```

A closure can provide the same kind of boundary:

```typescript
function Cash(digits, cents, currency) {
  const amount = `${digits}.${cents} ${currency}`;

  return {
    getAmount() {
      return amount;
    },
  };
}
```

<SectionHeading title="Are Objects with the Same State the Same Object?" />

```typescript
class Name {
  constructor(public readonly first: string, public readonly last: string) {}
}

const name1 = new Name("Hwanhee", "Jung");
const name2 = new Name("Hwanhee", "Jung");
```

`name1` and `name2` are different instances in memory. If their state is
identical, however, we can regard them as logically equal objects.

Equality is a human concept. Two things do not need to be physically identical
if they carry the same meaning. Treating equal states as equal values can:

- improve predictability,
- remove unnecessary conditional branches,
- simplify tests, and
- make caching and comparison easier.

An object should have a stable identity, and that identity should not change.
_When identity becomes unstable, the object becomes unstable too._

<Callout title="What does this mean for concurrency?" backgroundColor="gray">
  Shared mutable state is the central problem in concurrent environments.
  Multiple threads reading or changing one object can conflict, requiring
  synchronization through locks or mutexes. An immutable object never changes
  internally, so several threads can access it without observing a partial
  mutation.
</Callout>

# 3. Prefer Immutable Objects and Delay Mutability

> An immutable object cannot modify itself in any way. It must create and return
> a new object with the desired state.

The world itself is mutable. Addresses, bank balances, and even moods change.
That does not mean we cannot model the world with immutable objects. Immutable
objects shift our attention from _what was mutated_ to _how the state before
and after the change differs_.

<SectionHeading title="3.1. Why Use Immutable Objects?" />

```typescript
const five = new Cash(5);
const fifty = five.mul(10);
```

Several benefits are visible even in this small example.

**Predictability**

- `five` never changes.
- `fifty` is a completely different object.
- the two values do not unexpectedly share changing state.

**No bugs caused by observing a partial mutation**

A mutable object can expose an intermediate state:

```typescript
mul() {
  this.dollars *= 10;
  delay();
  this.cents *= 10;
}

cash.mul(10);
console.log(cash.print()); // May print an intermediate state
```

If an asynchronous interruption occurs between the assignments, another part
of the program may observe only half of the update. Once an object mutates,
programmers must track which line runs first and which line must follow it.

_Immutable objects avoid this problem because they never enter a partially
mutated state._

**Smaller objects**

An immutable object can initialize its state only when it is created. If a
constructor keeps growing, that pressure can reveal that the class owns too
many responsibilities and should be divided. The resulting objects tend to be
smaller and clearer.

<SectionHeading title="Immutability Resembles the Philosophy of Pure Functions" />

Working with immutable objects naturally encourages a style similar to pure
functions:

- input becomes output,
- side effects are avoided, and
- state is not shared through mutation.

OOP and FP are different paradigms, but both aim for predictable code and
separated complexity.

<Columns>
  <Column>
    **OOP**

    Objects own responsibilities and collaborate. Complexity is managed by
    separating responsibilities across objects.

  </Column>
  <Column>
    **FP**

    Functions transform data without changing state. Predictability comes from
    calculations without side effects.

  </Column>
</Columns>

Immutable OOP can therefore converge toward an object-design philosophy that is
close to pure functions.

<SectionHeading title="3.2. Rethinking What Immutable Means" />

Is this `WebPage` immutable or mutable?

```typescript
class WebPage {
  private readonly uri: URI;

  constructor(uri: URI) {
    this.uri = uri;
  }

  content(): string {
    // Performs an HTTP request, so the result is unpredictable
  }
}
```

The `uri` cannot change, and the object's structure remains the same. The result
of `content()`, however, depends on the web server and network.

The object can still be understood as a _faithful object_:

- it always refers to the same URI, and
- it faithfully reflects the current state of the real web page at that URI.

The object itself does not change, but the world it represents can change, so
its behavior can return a different result.

> An immutable object does not change itself, but it can faithfully respond to
> changes in the entity it represents.

<SectionHeading title="Identity, State, and Behavior" />

An object consists of an identifier, state, and behavior:

- **Identifier** — the reference, coordinate, or path that distinguishes it.
- **State** — the current state of the entity it represents.
- **Behavior** — the logic it performs when it receives a message.

For `WebPage`:

- the identifier is `uri`,
- the state is the page's current content, and
- the behavior is reading that state through `content()`.

The important point is that the object itself has not changed.

<SectionHeading title="Constant, Faithful, and Mutable Objects" />

A constant object has the same state and identifier. `Name("Hwanhee", "Jung")`
and `Point(3, 4)` are examples: their state is their identity, and neither
changes.

- **Constant object** — Its state is its identity. Both its meaning and content
  remain unchanged.
- **Faithful object** — The object is immutable, but it faithfully reflects
  changes in the external entity it represents.
- **Mutable object** — Its internal state can change, so it needs a separate
  identifier to preserve its identity over time.

Every constant object is immutable, but not every immutable object is constant.

# 4. Objects Collaborate, and Collaboration Needs Contracts

The central keyword in object-oriented design is _collaboration_.

<SectionHeading title="4.1. Objects Exist in Relationships" />

An object eventually encounters work it cannot perform alone. It uses, calls,
or depends on another object.

Dependencies have different strengths:

- **Tight coupling** connects objects directly.
- **Loose coupling** lets objects collaborate while knowing less about one
  another.

Tight coupling may not look harmful at first. As a project grows, however,
strongly connected objects make testing, refactoring, and change more
difficult.

<SectionHeading title="4.2. The World of Objects Resembles a Society" />

Objects perform responsibilities inside an environment. That environment is
social: relationships and collaboration are unavoidable.

The important question is not whether objects collaborate, but how tightly they
are coupled. Strong coupling makes tests harder, complicates refactoring, and
allows one change to spread like a domino effect.

We cannot remove collaboration, so we need a buffer between collaborators.

<SectionHeading title="4.3. The Interface Is That Buffer" />

> An interface is a contract that an object follows in order to collaborate
> with another object.

An object only needs to know the interface. It does not need to know how the
other object implements that contract.

```typescript
interface Cash {
  multiply(factor: number): Cash;
}
```

The interface states that any `Cash` must provide
`multiply(factor: number): Cash`.

```typescript
class DefaultCash implements Cash {
  constructor(private readonly dollars: number) {}

  multiply(factor: number): Cash {
    return new DefaultCash(this.dollars * factor);
  }
}
```

`DefaultCash` declares that it follows the `Cash` contract.

```typescript
class Employee {
  constructor(private readonly salary: Cash) {}

  doubleSalary(): Cash {
    return this.salary.multiply(2);
  }
}
```

`Employee` does not need to know the concrete `DefaultCash` implementation. It
trusts only the contract that a `Cash` provides `multiply`.

<SectionHeading title="4.4. An Object Can Follow Several Contracts" />

TypeScript supports multiple interfaces, allowing one class to fulfill several
roles:

```typescript
interface Shape {
  getArea(): number;
}

interface Printable {
  print(): void;
}

class PrintableCircle implements Shape, Printable {
  constructor(private readonly radius: number) {}

  getArea(): number {
    return Math.PI * this.radius * this.radius;
  }

  print(): void {
    console.log(`Area: ${this.getArea()}`);
  }
}
```

<SectionHeading title="4.5. Why Should Public Methods Belong to a Contract?" />

A public method is a point of contact with other objects. If public methods are
added without a contract or clear intention:

- callers may use them in unintended ways,
- teams cannot tell which methods are stable and which are internal,
- external code can become dependent on implementation details, and
- every object can develop a different usage pattern.

Interfaces make those collaborative expectations explicit and help preserve a
consistent design.

# 5. Unanswered Questions

Many questions remain unresolved.

<SectionHeading title="The Cost of Immutability" />

If every change returns a new object, does the design become too expensive in
memory or performance? Is continuously allocating objects always the right
tradeoff? The practical question is which approach remains easier to maintain.

<SectionHeading title="Why Is the UI Thread Single-Threaded?" />

Why not allow several threads to update the UI if multithreading can be faster?
Multiple threads trying to change the screen at the same time create races and
can leave the UI inconsistent during an interaction. Locks, queues, or
transactions would then be needed to coordinate every update.

For a UI, consistency is often more important than parallel mutation. Even
React's Virtual DOM comparison has its own cost, so the tradeoff is not simply
single-threaded versus fast.

<SectionHeading title="Does a Declarative Wrapper Really Matter?" />

Imperative code still runs somewhere underneath a declarative API. Is it
meaningful to say that we have made the code declarative merely by wrapping
that implementation? The important question may be where and how we design the
boundary.

<SectionHeading title="Do OOP and FP Solve the Same Problem Differently?" />

OOP and FP can look like opposites. The more I study them, however, the more
they seem to pursue similar goals in different languages.

Other questions remain:

- Where should we draw the line between getters and methods?
- How should we model time and events if objects are truly collaborating
  participants?
- In frontend code, is a user interaction a command or a message?
